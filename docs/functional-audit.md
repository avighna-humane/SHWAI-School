# SHWAI Functional Audit Baseline

## Audit date

14 August 2026.

## Architecture finding

The repository is a React 19 + TypeScript + Vite + TanStack Start application. It has a TanStack Router route tree, a client-side app-state provider, Tailwind/shadcn UI primitives, deterministic mock datasets, and a small set of TanStack Start server functions. It does not contain a real authentication flow for school users, a complete server-side authorization context, a complete schema/migration system, a test suite for SHWAI workflows, background jobs, file storage, or a configured AI provider in the application runtime.

The existing database helper uses `DATABASE_URL`, while the standalone migration script uses `SUPABASE_DATABASE_URL`. The initial persistence boundary contains PostgreSQL tables for homework, submissions, notices, notice reads, and chat messages. Those workflows are real database writes when a database is configured, but their handlers currently trust client-supplied `schoolId`, `role`, and user identifiers. The UI also falls back to deterministic demo identities and local storage for the selected role, school, plan, and notification state.

## Security baseline

The existing route-level role filters and plan gates are useful presentation controls but are not sufficient server-side authorization. Any persisted operation that accepts a school, role, or actor identifier from the browser must be treated as unsafe until it is bound to a server-issued session and checked against an authorization policy. The implementation in this change therefore treats the demo session as an explicit, signed development boundary and does not claim production identity or cross-tenant isolation without a real identity provider and database-backed user membership records.

## Completion policy

Mock datasets remain available for demonstrations and empty-state testing. They are not considered production data. A workflow is only marked functional when it has a server service boundary, input validation, persistence, authorization checks, auditability where relevant, and UI loading/error/success behavior. Features requiring unavailable external credentials remain explicitly configuration-required.
